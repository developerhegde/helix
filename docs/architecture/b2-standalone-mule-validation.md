# B2 architecture decision — standalone Mule validation

## Decision

Helix remains standalone. B2 must not import, invoke, vendor, or require Meridian. Helix will own a narrow Mule-project validation subsystem behind `helix validate`, with deterministic input/output contracts and no dependency on a client estate, platform inventory, or deployment state.

The subsystem validates only what B2 needs to decide whether generated code is safe to present in a pull request:

1. The project compiles and packages through Maven and MUnit.
2. The generated project uses only approved Maven coordinates, plugins, repositories, runtime version, and property-file sources.
3. Every configuration reference in Mule XML and DataWeave is either defined in the generated configuration files or explicitly declared by the approved design bundle as a deployment property.
4. Secrets are placeholders or secure-property references, never plaintext values.
5. Environment-specific placeholders occur only where the approved design bundle expects them.
6. The generated source and tests agree with the approved design bundle: contract, design documents, mapping anchors, property keys, and expected test coverage.

This is a B2 code-quality and evidence boundary. It is not an estate-comparison, drift-management, deployment-readiness, or platform-governance product.

## Why this decision

The previous LLD delegates B2 validation, naming, property preparation, and audit support to Meridian. That contradicts the standalone B1 decision and couples B2 delivery to Meridian's runtime configuration, state files, credential model, and release cadence.

Helix can instead own the small, deterministic checks needed before opening a pull request. Platform inventory comparison, environment reconciliation, and deployment-specific validation remain out of B2 and can be introduced later through an explicit optional adapter.

## Architecture

```text
Approved design bundle
        │
        ├── Helix project validator ──► validation report
        │       ├── project structure and design artefact integrity
        │       ├── Maven/POM policy
        │       ├── Mule and DataWeave reference scan
        │       ├── configuration/secret/marker checks
        │       └── mapping and test evidence checks
        │
        └── Maven/MUnit verifier ────► build and test evidence
```

### Core modules

| Module | Responsibility | Network access |
| --- | --- | --- |
| `helix.validation.design_binding` | Hash-check approved contract, HLD, LLD, and design bundle against the current project tree. | None |
| `helix.validation.pom_policy` | Parse `pom.xml`; enforce the golden parent, pinned Mule/MUnit versions, approved plugins, no project repositories, and no forbidden wrappers/extensions. | None |
| `helix.validation.reference_scan` | Parse Mule XML and DataWeave source to collect property and secure-property references, mapping anchors, flows, APIkit operations, and outbound processor declarations. | None |
| `helix.validation.property_policy` | Compare referenced keys with generated configuration files and `design_bundle.deployment_property_keys`; enforce property classes and placeholder placement. | None |
| `helix.validation.secret_policy` | Detect plaintext secrets and unfilled/incorrect markers using Helix-owned rules. | None |
| `helix.validation.project_policy` | Enforce generated-tree policy: no CI/workflow files, Maven wrapper files, unapproved Java interop, or unapproved configuration sources. | None |
| `helix.validation.report` | Produce `validation_report.v1`, deterministic findings, and a concise pull-request evidence summary. | None |
| `helix.verify` | Orchestrate the local validators with Maven/MUnit in an isolated verify container. | Maven proxy only for Maven resolution |

Every module is pure or file-bound. It receives explicit paths and the approved design bundle; it does not read a profile directory, a home directory, process-wide configuration, or external system state.

## Input contract

`helix verify` receives:

- A generated project tree.
- The gate-two-approved `design_bundle.v1` and its SHA-256.
- The approved contract, HLD, and LLD with their SHA-256 values from the bundle.
- A Helix-owned `validation_policy.v1` selected by the client profile, but staged as an immutable input for the attempt.
- Test evidence generated by Maven and MUnit. The isolated verifier writes `target/helix-validation-evidence.json` (`mule_validation_evidence.v1`) with Maven exit code, MUnit test/failure/error counts, and application coverage; `helix validate` consumes only this value-free summary.

It does not receive Meridian files, platform credentials, Anypoint inventory, state directories, or deployment captures.

## Validation policy

`validation_policy.v1` is a versioned, client-selectable but Helix-owned data contract. Its initial version contains:

```yaml
schema: validation_policy.v1
version: 1
standards_bundle_digest: <SHA-256 of the staged client standards bundle>
maven:
  golden_parent: {groupId: example, artifactId: acme-mule-parent, version: 1.0.0}
  allowed_plugins: [org.mule.tools.maven:mule-maven-plugin]
  mule_runtime: 4.9.1
  munit_version: 3.7.4
project:
  forbidden_paths: [.github/**, .gitlab-ci*, Jenkinsfile, .mvn/**, mvnw*]
  forbid_java_interop: true
configuration:
  allowed_property_sources:
    - src/main/resources/config/config.yaml
  environment_selector: env
  secure_property_key: secure.key
  marker_prefix: HELIX
testing:
  minimum_application_coverage: 75
```

| Section | Meaning |
| --- | --- |
| `standards_bundle_digest` | Binds the policy to one approved standards bundle; a design bundle carrying another digest fails with `STANDARDS_BUNDLE_MISMATCH`. |
| `maven` | The client's parent POM, by exact coordinates, plus the plugins and runtime a generated POM may declare. The parent POM is owned and published by the client; Helix pins it and never writes it. |
| `project` | Paths a generated tree may not contain, and whether Java interop is refused. |
| `configuration` | The base property source, the deployment-supplied selector and secure-key names, and the mark prefix. |
| `testing` | The minimum application coverage. The default is 75, the value in `docs/mulesoft-development-standards.md`; a client may raise it in its standards bundle. |

The policy is compiled, never written by hand: `helix stage --profile <dir> --out-dir <dir>` refuses an unhealthy profile, then writes `validation-policy.json`, `naming-contract.json` and a byte copy of the standards bundle into a new directory, the three inputs of LLD 07 §3.4.4. `helix.validation.policy_compiler.compile_policy` takes `maven`, `project`, `testing` and the standards checks from the approved bundle and `configuration` from the naming contract, so the three cannot disagree. Nothing in it comes from a ticket or a model. The coverage minimum is 75 when the bundle is silent, and the mark prefix is the product's identifier unless the bundle sets one.

**Marks.** A value owed after merge is written as `${HELIX_SET_<ENV>}`, and an owed secret as `${HELIX_ENCRYPT_<ENV>}`, where `<ENV>` is the naming contract's environment key. The prefix is policy data, so a product rename or a client convention changes one field and no validator code.

### Standards checks

These sections are optional. Each field switches on one check taken from the client standards; a policy without the field skips it. Patterns are regular expressions that must match the whole name.

| Field | Check | Finding |
| --- | --- | --- |
| *(always)* | No version range, `LATEST` or `RELEASE` in the POM | `POM_VERSION_RANGE` |
| `maven.child_pom.forbid_versions`, `forbid_profiles`, `forbid_final_name`, `require_semver`, `artifact_is_repository_name` | The child POM pins no version, declares no profile, keeps `finalName`, uses MAJOR.MINOR.PATCH, and is named for the repository | `POM_VERSION_DECLARED`, `POM_PROFILE_DECLARED`, `POM_FINAL_NAME_OVERRIDDEN`, `POM_VERSION_NOT_SEMVER`, `POM_ARTIFACT_MISMATCH` |
| `maven.group_id`, `maven.allowed_connectors` | The organisation's `groupId`; connectors only from the approved coordinates | `POM_GROUP_MISMATCH`, `POM_CONNECTOR_NOT_ALLOWED` |
| `project.mule_artifact {min_mule_version, java, secure_key}` | `mule-artifact.json` states the runtime and Java version and lists every secret key and the secure key | `MULE_ARTIFACT_INVALID` |
| `patterns.{implementation_flow, sub_flow, connector_config, flow_variable, error_type, object_store, property_key, feature_flag, dataweave_script, dataweave_module}` | Names and paths follow the standard | `NAME_PATTERN_VIOLATION` |
| `mule.error_handler_file`, `forbid_on_error_continue_any`, `require_request_validation` | One global error handler in the named file; no continue on every error; one APIkit router with validation on | `ERROR_HANDLER_MISPLACED`, `ON_ERROR_CONTINUE_ANY`, `APIKIT_ROUTER_NOT_SINGLE`, `APIKIT_VALIDATION_DISABLED` |
| `logging.forbid_free_text_logger`, `log_event_subflow` | No `<logger>` outside the approved sub-flow | `FREE_TEXT_LOGGER` |
| `testing.forbid_sleep`, `ignored_needs_ticket`, `suite_per_implementation` | No sleep; an ignored test names a ticket; each implementation file has a suite | `TEST_SLEEP`, `TEST_IGNORED_WITHOUT_TICKET`, `TEST_SUITE_MISSING` |

A Mule XML file that is not well-formed is `MULE_XML_INVALID` when any of these checks is on. Findings carry fixed text and never a name, so a report cannot leak a value through a name.

`marker_prefix` and `environment_selector` are enforced when the naming contract is staged. Not yet enforced: `munit_version` and `secure_property_key`.

## Reference and property rules

The reference scan recognizes, at minimum:

- Mule `${key}` expressions.
- Mule `${secure::key}` expressions.
- DataWeave property lookups and secure-property references supported by the chosen generated-code patterns.
- APIkit operations in the approved contract.
- `// map:MAP-nnn` mapping anchors emitted by generated DataWeave.

The validator creates these deterministic sets:

- `K_code`: property and secure-property references found in source.
- `K_defined`: keys in generated base, environment, and secure configuration files.
- `K_deployment`: `deployment_property_keys` in the approved design bundle.
- `K_expected`: approved design-bundle keys.

The build is valid only when:

```text
K_expected == K_code - K_defined + K_deployment
```

and every key's class, file placement, type, and marker state matches the design bundle. Dynamic property references are rejected in B2 because they cannot be proven against the approved key list.

## Secret and marker rules

- A secret value must use a secure-property reference and an `ENCRYPT` marker in an environment-specific secure configuration file, or be declared as a deployment property.
- A plaintext secret-shaped value is a blocking finding.
- `SET` and `ENCRYPT` markers are allowed only for a key and environment the design bundle explicitly owes.
- Markers are prohibited in base and test configuration files.
- Test configuration uses synthetic fixture values, never markers or client values.
- A deployment property is declared in the design bundle but not written into generated configuration files.

## Evidence and outcomes

`validation_report.v1` must include:

- Validator-policy version and digest.
- Design-bundle and member-file digests.
- POM-policy result.
- Referenced, defined, and deployment property-key sets; never property values.
- Marker and plaintext-secret findings by path and line.
- Contract-to-flow and mapping-anchor coverage results.
- Forbidden-tree-path and Java-interop results.
- Maven/MUnit evidence summary: exit code, test/failure/error counts, and coverage percentage; never logs, payloads, or property values.
- A deterministic overall verdict: `pass`, `fail`, or `incomplete`.

`fail` means the generated project violates the approved design or a safety policy and returns `RETRY_BUILD` while retry budget remains. `incomplete` means a required verifier could not run, such as Maven/MUnit infrastructure unavailability, and opens only a draft PR marked INCOMPLETE. `pass` is necessary, but not sufficient, for test acceptance: MUnit coverage, assertion checks, mock checks, and mutation checks remain independent B2 controls.

## Explicitly deferred

The following are not B2 responsibilities:

- Meridian `report` and `prepare` behavior.
- Platform estate discovery, drift comparison, or runtime collections.
- Inventory CSVs, environment promotion, endpoint captures, or deployment assertions.
- Platform policy validation that requires Anypoint access.
- Automatic configuration propagation between environments.

A future `meridian_adapter` or other provider adapter may add these capabilities. It must be optional, version-pinned, invoked only through an adapter interface, and covered by contract tests. Core B2 validation remains functional with no adapter installed.

## Acceptance criteria

The design is ready for B2 implementation when Claude Code can build a synthetic project that proves all of these cases:

1. A golden project passes local validation and Maven/MUnit verification.
2. An unapproved Maven repository, plugin, runtime version, wrapper, workflow, or Java-interop source fails validation.
3. A property referenced in source but absent from both configuration and `deployment_property_keys` fails validation.
4. A design key not referenced by generated source fails validation.
5. A plaintext secret, an unexpected marker, or a marker in a base/test file fails validation.
6. An approved contract, HLD, LLD, or design bundle changed after gate two fails integrity validation.
7. A missing mapping anchor, uncovered API operation, or dynamic property reference fails validation.
8. All reports are deterministic and contain no client values, secrets, or external-system data.
9. The full validator runs with no Meridian dependency and no network access beyond Maven resolution through the approved proxy.

## Consequences for the existing LLD

Before B2 implementation, revise LLD files 01, 02, 04, 06, 07, 08, 09, 10, and 11 to distinguish:

- Helix core behavior, which must work standalone.
- A future optional Meridian adapter, which must not be required by B1 or B2.

The immediate implementation focus is `07-b2-build-test-pr.md`: replace `meridian report`, `prepare`, naming, and reference-scan requirements with this Helix-owned validation subsystem. Do not implement the Meridian adapter during B2.
